# 开发团队建设路径评估：自研产品、开源二开与 WorkBuddy

版本：v2.1 同范围投入对照稿  
公开来源核验日期：2026年9月8日  
本轮补齐：与需求 v1.6 对齐工作量、费用及未决结论；未新增厂商实测或报价  
决策主体：本产品开发团队与产品负责人  
目标：建设可向高校交付的 AI 数字员工通用客户端与管理后台  
关联需求：[通用平台需求规划](</Users/kakarrot/Dev/AI Employee OS/docs/client-requirements-plan.md>)  
边界：分析团队如何建设、复用什么、承担多少工作及如何选型。具体业务场景与技术实现方案继续留空。

## 一、结论

**建议保留自有产品形态，以当前 AI Employee OS 工程为基础继续建设，按明确缺口复用开源组件或采购成熟能力。整套开源二次开发作为对照方案，WorkBuddy 生态应用作为另一种交付形态评估。**

评价重点是开发团队达到目标行为所需的剩余工作、长期维护、产品控制权和资源。学校采购预算、其他学校成交价、教职工节省工时不参与这次建设方式的成本比较。

结论分为两层：产品上保留自己持续维护的客户端与后台，统一发布、授权、事项、结果与审查规则；建设上复用已经满足要求的能力，不为“自研”标签重复开发。开源源码、商业组件和 WorkBuddy Managed Agents 都可能成为自有产品的能力来源。

当前工程已有可复用基础，而尚无实测证明整套开源替换或 WorkBuddy 生态配置能以更低完整成本满足目标，因此建议先保留现有路线。这是基于当前证据的默认方向，不是完整成本评估后的定案；对照方案验证胜出后应调整选择。历史投入本身不是继续自研的充分理由。

## 二、比较对象必须分清

### 2.1 三条建设路径

| 路径 | 团队实际做什么 | 形成什么资产 | 主要责任 |
| --- | --- | --- | --- |
| A．以现有工程为基础自研独立产品 | 自己维护核心客户端、后台与产品规则，复用成熟服务或局部组件 | 自有产品代码、配置、发布版本、测试与交付材料 | 缺口建设、整合、验证、发行和支持 |
| B．以完整开源平台为基础二次开发 | 选择一个主底座，理解并改造其产品对象、权限和交付方式 | 遵循上游许可的衍生产品，自有改造与上游代码并存 | 适配、补齐、迁移、上游升级和修复 |
| C．依托 WorkBuddy 提供应用或能力 | 使用宿主交互与管理能力，开发应用、专家、技能、连接器和必要配套服务 | WorkBuddy 生态产品或解决方案，以及自建能力资产 | 能力开发、宿主适配、配置测试、发布与支持 |

A 与 B 都可以形成自有产品，区别在于核心产品代码与规则由哪里承载。A 也可以复用开源，不能把 A 假设成所有能力从零建设；如果只引入局部组件，属于 A 的复用，而非整套平台替换。

“采购开源”应拆成获取公开许可下的源码、购买商业授权或企业功能、购买实施与支持。免费获取源码不代表总成本为零，商业授权也不自动表示获得全部源码和任意再分发权。

### 2.2 四种 WorkBuddy 用法

| 用法 | 与自研的关系 | 选型含义 |
| --- | --- | --- |
| 用 WorkBuddy 帮团队写代码、资料和测试 | 仍是 A 或 B，它是开发工具 | 计入开发工具成本，不自动成为交付产品的运行依赖 |
| 在 WorkBuddy 中发布应用、专家、技能与连接器 | 属于 C | 复用宿主体验与分发，需核对开放范围和目标行为 |
| 保留自有客户端，接入企业智能体／Managed Agents | 可以属于 A 的商业能力复用 | 比较剩余产品工作、服务费用、运行控制和退出成本 |
| 购买企业版、私有化或品牌定制 | 取决于准确合同和交付内容 | 企业管理或品牌设置不等于取得全部源码，也不自动等于任意改造和转售独立客户端 |

WorkBuddy 开放平台已说明支持技能、专家、专家团、连接器和外部应用接入，并有认证、测试、审核、发布流程，因此不能将它描述为只能个人使用的聊天工具。[开放平台说明](https://open.workbuddy.cn/docs/what-is-open-platform)

企业智能体文档提供自有系统接入说明，Managed Agents 官方介绍也列出开发者接入能力。采用这类服务不必放弃自有产品，关键是准确服务范围与交付条件。[企业智能体文档](https://www.workbuddy.cn/docs/enterprise/adminguide/CloudAgent)、[Managed Agents 介绍](https://intl.cloud.tencent.com/zh/products/workbuddy-managed-agents)

不能以安装成功、单次问答或一个工作流完成替代全范围验证；也不要求外部平台复刻当前原型布局，重点比较目标行为，界面差异作为明确的产品取舍记录。

### 5.2 对本项目的结论

在 WorkBuddy 中开发能力是可研究的正式建设路径，尚不能直接认定为完整通用平台的等价替代。它可能减少客户端和部分管理建设，但如果仍要另建完整后台、授权和事项管理，应把这些工作计回 C，而不能只报价几份 Skill 的开发。

如果团队接受 WorkBuddy 宿主体验，目标行为可达到，发布、资料及商业条件成立，C 可以成为正式方案。此时需要明确调整交付边界，不能按 C 省略建设，同时继续承诺 A 的全部独立产品能力。

如果需要保留自有客户端与后台，应单独评估企业智能体／Managed Agents 接入；这属于服务复用，不等于把全部产品改成 WorkBuddy 插件。若只是用 WorkBuddy 帮团队写代码，则仍属于 A／B，代码审查、验收和长期维护责任仍由本团队承担。

## 六、团队投入与控制能力比较

以下是依据产品形态的定性分析，不是实测分数。实际速度和费用按第七、八节验证。

| 比较维度 | A．现有工程自研 | B．整套开源二开 | C．WorkBuddy 生态交付 |
| --- | --- | --- | --- |
| 首次可用版本 | 复用当前基础，补前后台闭环 | 适配程度决定速度，安装不等于完成 | 适配宿主时可能较快，配套服务仍需开发 |
| 自有界面与规则 | 由团队定义维护 | 可以修改，受上游结构与许可影响 | 受开放能力约束，可定制程度需核验 |
| 现有资产 | 优先核查复用员工、事项与控制逻辑 | 计入对象、资料、历史与界面迁移 | 能力包可能复用，独立客户端不自动成为交付部分 |
| 后台缺口 | 团队补齐 | 复用通用部分并补目标规则 | 核对宿主管理覆盖度，额外后台不能漏算 |
| 验证责任 | 自有改动与外部能力 | 上游、自有改造和集成 | 自有能力、宿主交互和平台升级 |
| 长期维护 | 自有代码与依赖维护 | 额外承担上游合并、分叉和迁移 | 平台兼容、发布流程及持续费用 |
| 产品控制与退出 | 自有部分可控，外部依赖仍须核对 | 保有许可范围内源码，并需具备接手维护能力 | 依赖开放范围、协议与导出，迁移能力需实测 |
| 当前建议 | 默认保留，优先局部复用 | 作为整套替换对照，验证胜出可改选 | 作为交付形态候选，先证明目标满足度 |

推荐 A 的实际依据是已有基础和明确的跨模块目标，尤其是单一发布来源、授权变化、本人确认、未知结果与只读审查。采用 B／C 若能更少投入地满足这些行为，同样可以选；品牌或“自研”称号本身不能证明成本收益。

## 七、从开发团队角度算成本

按相同目标行为、使用规模和支持范围，比较从现在开始的 12 个月投入，并补充 36 个月维护预测。计入产品、设计、开发、测试、交付和运维，不只计算写代码人天。

`总投入 = 剩余建设人力 + 学习适配 + 迁移 + 验证交付 + 许可与工具订阅 + 实际服务用量 + 持续维护 + 退出迁移准备`

| 成本项 | A 记录什么 | B 记录什么 | C 记录什么 |
| --- | --- | --- | --- |
| 建设 | 当前缺口、新增后台、两端贯通 | 上游学习、改造和目标缺口 | 应用、专家、技能、连接器及配套服务 |
| 迁移整合 | 外部能力与现有产品整合 | 当前对象、资料、历史与界面迁移 | 能力迁入宿主，原独立产品部分的保留或退出 |
| 验证交付 | 全链路与外部能力 | 上游、自有修改和升级回归 | 宿主边界、能力测试、发布和升级回归 |
| 许可服务 | 开发工具、组件和模型用量 | 商业授权、支持、资源和模型 | 开发工具、企业权限、实际使用席位、积分与服务费用分列 |
| 持续维护 | 自有产品和依赖 | 自有分叉和上游同步 | 宿主变化、兼容、发布与支持 |
| 退出 | 外部能力替换 | 上游停止维护后的接手与迁移 | 配置、资料、运行证据取回与替代建设 |

各项只计一次，旧资产的后续改造计入，历史投入单列。开发团队使用 WorkBuddy 的席位，与最终运行方案需要的用户授权不同，应分别核实数量和承担方；不能把几个开发者账号当作整套产品的全部运行成本。

### 7.1 当前价格依据

WorkBuddy 官方计费概述列出 SaaS 企业版 198 元／人／月、1 席起购；专有云企业版 316 元／人／月、100 席起购；私有化需咨询，积分加量另计。这里只记录对应档位公开标价，不将其视为 Managed Agents 集成、对外提供服务或完整交付的总报价。[官方计费](https://cloud.tencent.com/document/product/1831/134333)

开源源码获取、商业授权和支持分开核算。Dify 企业版为定制报价；Coze Studio 社区源码许可不包含面向本团队的商业支持承诺。不同产品与计费单位不能按标价直接排名。[Dify 企业版](https://dify.ai/zh/pricing/dify-enterprise)、[Coze Studio 许可](https://github.com/coze-dev/coze-studio/blob/main/LICENSE-APACHE)

### 7.2 怎样判断复用有收益

`复用净收益 = 避免的剩余自建投入 − 新增适配、迁移、许可、用量差额、维护与退出投入`

同一期间、同等目标行为下净收益为正，且关键控制和交付条件成立，才可判断复用在成本上更有利。更早取得可验证版本可以记录为时间收益，没有依据时不折算成销售收入；学校购买价与学校侧工时节省不代入该公式。

## 八、选型验证与改变结论的条件

使用主文档 M11 的单专家、固定串行、人工确认、版本回退、异常恢复五组通用配置。A 记录已有与缺口；B 指定准确开源版本；C 写明客户端、企业版、开放应用还是 Managed Agents，不混用各档位能力。

| 核对项 | 必须证明的产品行为 | 同时记录的工作量与需求 |
| --- | --- | --- |
| 配置发布 | 同一发布来源，草稿不改写历史，停用影响可说明 | 配置适配、版本与两端贯通；H02、H03、H09、B01—B02 |
| 授权资料 | 有权与无权访问、撤权生效、外部主数据只读 | 身份映射、范围和资料治理；H01、H06、H10、M03、M09 |
| 事项确认 | 不重复生成请求，有权人员处理本人决定，拒绝不执行 | 对象映射与必要控制；F04—F06、M05 |
| 失败与未知 | 不假报完成、不盲目重做，恢复责任与证据可见 | 状态适配、核验和恢复；F05—F07、H05 |
| 运行审查 | 结果可核验，逐次记录可查，审查不变成代操作 | 记录、查询与权限；H05、M04、M06 |
| 维护退出 | 能升级一版，取回约定配置、资料和历史 | 上游冲突、宿主变化、导出与替代工作 |

比较以行为为准，不要求复制原型布局。界面与操作差异单列产品取舍，权限、真实结果和必要证据不能通过暗改需求降低标准。五组筛查后仍须 A01—A36、M01—M11 的完整验证。

选择规则：

1. **继续 A：**已有基础可复用、剩余工作可承担，整套替换尚未证明减少完整投入；局部组件或服务有收益时照常采用。
2. **改选 B：**核心规则适配、许可清楚、迁移升级通过验证，且补齐全范围投入更少；明确唯一主底座，避免重复维护配置与状态。
3. **改选 C：**团队接受 WorkBuddy 生态交付，目标行为、商业与发布条件成立，完整投入更合适；同步调整交付边界。
4. **采用 Managed Agents 等能力：**保留自有产品时能减少建设工作，可纳入 A；验证目标入口、费用与行为后决定，不因产品名称预先排除。

产品负责人确定必要行为和可调整体验，开发负责人估算剩余工作，测试负责人核查证据，项目负责人确认资源和选择。无需将此问题转成“学校应自研还是采购”。
