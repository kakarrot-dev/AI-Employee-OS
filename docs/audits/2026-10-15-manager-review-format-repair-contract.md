# 总管审核格式纠正与 4B 前置门禁

用户已授权：修复总管输出格式错误引发员工重复返工；格式纠正复用现有证据，避免重做已完成工具；Poe 自然语言多员工任务与审批恢复通过后进入 4B；保护所有未提交修改。

## 修复边界

1. 将总管响应分为有效业务审核和格式错误。根结构、逐项验收结构、交付正文结构或已批准结果的 DeliveryResult 校验失败，属于格式错误；结构有效且业务 criteria 不通过，仍走现有员工返工和真实证据门禁。
2. 格式错误只请求总管纠正。每个完成批次最多允许 2 次格式纠正，全部计入原 Run 的 Provider 步数、Token、截止时间，不扩充权限或预算；到上限明确失败，不分派员工。
3. 第一次最终审核保存完整 Provider 请求与冻结证据摘要，包括 TaskRevision/RunGrant、已完成 Assignment、Handoff、ToolAction 结果和 ResearchBundle。纠正使用原请求的证据和 schema，加上精确错误码与有界无效结果；不重新读取工具、不回忆新增记忆、不重新执行分批文档审核或物化交付。
4. 当前完成批次的证据变化必须拒绝；真实业务返工后产生新的 Assignment/Handoff 才开启新批次。检查点持久化纠正计数和原请求，重启、正常退出和拒绝计划变更不能重置计数或绕过已保存证据。
5. SDK、历史执行器都沿用现有 Runtime/Provider 路径。原 Approval/Grant、ToolGateway、未知结果及历史 worker 路径保留。无有效总管结论时不能生成 Delivery。
6. SDK 总管审核只使用 Runtime 已冻结的完整审核请求，不再额外拼接变化中的 root history。格式纠正已存在的业务批准/逐项判断必须保持；模型不得以把 approved 改成 false 来触发员工返工。原业务门禁仍独立核验真实证据。显式 `invalid_structured_output` 接入同一总管纠正流程，取消、网络和授权错误不转为格式纠正；旧 Poe 解析也先保留实际 usage 再校验输出。

## 验证顺序

- 先用上阶段真实失败结果复现：合法文件已经存在、总管交付指标不合约，不应新增 Assignment 或 ToolAction。
- 确定性覆盖：格式纠正成功；多种结构错误；纠正上限；真实业务失败仍返工；证据损坏；重启/退出/变更后的计数恢复；原预算不足或超时失败；长文档复用已有审核摘要；并发与过期响应不污染新批次。
- 运行相关后台测试、类型检查和构建；用独立数据与真实 Poe 重跑自然语言双员工文件任务、审批点 SIGKILL 恢复、拒绝和取消，并补测已保存失败证据到格式纠正的真实 Provider 闭环。
- 保留所有成功和失败样本，不以重试后成功掩盖模型失败或放宽原交付证据校验。
- 上述门禁通过后进入 4B：先记录当前实际调用/Token/耗时/进程内存/构建与依赖体积基线，再选择有证据、可独立验证的减重项；每项变更仍需治理与恢复回归。禁止由迁移标签推断性能收益。
