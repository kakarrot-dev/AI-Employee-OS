## 变更与权威边界

`TaskService.runtimeDispatchContext` 校验 activeRun、唯一 running Assignment、冻结员工版本、前序完成状态、员工请求 ID、provider_step 与原始输入摘要。`TeamExecutor` 随后提交带 `runtime_frozen_plan` 来源的检查点，再把精确 Assignment 交给原 SDK `Agent.asTool()` 子员工。

该控制响应使用 SDK 原生 function_call，Usage 为零，不发 Provider 请求、不创建付费 provider_step 或 BudgetLedgerEntry。SDK 图名、执行器 `openai-agents-ts-v2`、SDK 0.20.0 和冻结 binding 算法保持兼容。自然语言路由、员工推理、最终审核与格式纠正仍使用既有 Provider。Task、Run、Grant、审批、工具网关、Handoff 校验和 Delivery 均由原 Runtime 决定。

dispatch 是向后兼容的联合回执：新回执绑定员工版本、Assignment、员工请求和稳定 callId；历史无来源标签的 `{assignmentId, request, events}` 继续读取，并仅重放已接受的响应。历史实际调用和 Token 仍保留，不回写成零。检查点校验还拒绝跨 Assignment、员工、请求或 callId 的回执。

审批对照更接近相同执行轨迹：都执行一次创建、一次回读及相同后续阶段。付费分派从 2 次、3,663 Token 变为零；总 Token 实际减少 3,603，其余阶段净增加 60 Token。

## 恢复与真实副作用

- 两个新版自然语言任务都冻结相同的两名员工，依次完成 DOCX 读取、已校验交接、文档创建和真实回读。每例只有 2 个 Assignment、3 项成功工具动作、一次文件写入；文件 SHA-256 与回读回执一致。没有员工返工。
- 新版待审批处 SIGKILL，再以同一数据库恢复：同一 Approval、同一 Grant，等待期间零模型调用，批准后写入一次并完成回读与交付。
- 使用修改前 Runtime 真实创建旧版待审批检查点，随后换成新 Runtime 恢复：完整嵌套 RunState 和 prepared-before-RunState 两种路径均通过。后者只在隔离测试库截去后续 SDK 检查点，以重现崩溃窗口。两者均保持无标签的旧分派回执和原审批/Grant；各恢复后 3 次实际模型请求、零新增付费分派、无重复请求或写入。
- 审批拒绝：未写文件、无 Delivery、SDK 状态 rejected。取消：未进入下游员工、无工具副作用。两种负向场景前后构建都按预期关闭。
- 所有探针均未提供 DeepAgents worker 参数，也未创建 worker 检查点目录；工具和文件处理仍走现有生产实现。使用隔离夹具员工，未覆盖第三方 MCP、远程写入或完整 GUI 人工验收。
